# 프로젝트 개발 컨벤션

## 1. 목적

이 문서는 STORY / REELS 프로젝트의 코드 작성 방식과 Git 협업 규칙을 통일하기 위한 기준을 정의한다. 코드 가독성을 유지하고 A·B·C 담당자의 작업을 원활하게 통합하는 것을 목표로 한다.

본 문서는 팀 공통 컨벤션 초안이며, API·DB 구조 및 공통 필드 변경은 관련 담당자와 합의한 뒤 적용한다.

## 2. 코드 작성 규칙

### 2.1 Python 네이밍

- 변수명과 함수명은 `snake_case`를 사용한다.
- 클래스명은 `PascalCase`를 사용한다.
- 상수명은 `UPPER_SNAKE_CASE`를 사용한다.
- 함수와 변수는 역할을 명확하게 나타내는 이름을 사용한다.
- 한 함수는 가능한 한 하나의 책임을 갖도록 작성한다.

```python
def get_user_conversations(user_id: int):
    ...

class ConversationService:
    ...

MAX_HISTORY_COUNT = 50
```

### 2.2 파일 및 모듈 구성

- 관련 기능은 목적에 맞는 디렉터리와 모듈로 분리한다.
- 파일 하나에 서로 다른 계층의 책임을 과도하게 집중하지 않는다.
- 기존 프로젝트의 디렉터리 구조를 우선 따르며, 구조 변경이 필요하면 팀원과 공유한다.

권장 역할은 다음과 같다.

| 영역 | 책임 |
|---|---|
| `routers/` | HTTP 요청 처리 및 응답 반환 |
| `schemas/` | 요청·응답 데이터 검증 |
| `models/` | 데이터베이스 모델 정의 |
| `services/` | 핵심 비즈니스 로직 |
| `dependencies.py` | 공통 의존성 주입 |
| `database.py` | DB 연결 및 세션 관리 |
| `security.py` | 인증 및 보안 관련 기능 |

실제 파일 구조와 기존 코드가 우선이며, 모든 기능을 반드시 위 구조에 맞춰 새로 분리할 필요는 없다.

## 3. API 컨벤션

### 3.1 엔드포인트

- URL은 리소스를 기준으로 작성한다.
- HTTP 메서드는 작업의 의미에 맞게 사용한다.
- 기존 엔드포인트를 변경하거나 삭제할 때는 호출하는 담당자와 먼저 조율한다.

예시:

```text
POST   /auth/register
POST   /auth/login
GET    /conversations
POST   /conversations
GET    /conversations/{conversation_id}
```

위 경로는 예시이며, 실제 프로젝트에서 이미 사용 중인 API 규격과 일치하는지 확인한 뒤 적용한다.

### 3.2 요청 및 응답

- 요청과 응답의 데이터 구조는 Pydantic 스키마로 명시한다.
- 필드명, 자료형, 필수 여부, 오류 응답 형식을 일관되게 유지한다.
- 공통 응답 형식을 도입하거나 변경할 때는 A·B·C 담당자가 함께 합의한다.
- 기존 API의 요청·응답 구조를 임의로 변경하지 않는다.

### 3.3 HTTP 상태 코드

- `200 OK`: 요청 성공
- `201 Created`: 리소스 생성 성공
- `204 No Content`: 응답 본문 없이 요청 성공
- `400 Bad Request`: 잘못된 요청
- `401 Unauthorized`: 인증 정보가 없거나 유효하지 않음
- `403 Forbidden`: 접근 권한 없음
- `404 Not Found`: 리소스를 찾을 수 없음
- `422 Unprocessable Entity`: 요청 데이터 검증 실패
- `500 Internal Server Error`: 예상하지 못한 서버 오류

상태 코드는 실제 오류 상황에 맞게 선택하고, 기존 API의 동작과 일관성을 유지한다.

## 4. DB 및 인증 컨벤션

- DB 모델과 필드의 이름, 자료형, 제약 조건을 명확하게 정의한다.
- DB 스키마 변경은 관련 API 및 서비스에 미치는 영향을 확인한 뒤 적용한다.
- 인증이 필요한 API는 프로젝트의 공통 인증 의존성을 사용한다.
- 사용자 소유 리소스는 서버에서 인증된 사용자 정보를 기준으로 접근 권한을 확인한다.
- 요청으로 전달된 사용자 ID만 신뢰해 다른 사용자의 데이터에 접근하도록 허용하지 않는다.
- 비밀번호는 평문으로 저장하지 않고 안전한 해시 방식으로 처리한다.
- 비밀 키, DB 비밀번호, 토큰 등 민감한 정보는 소스 코드에 직접 작성하거나 Git에 커밋하지 않는다.
- 환경 변수는 `.env`로 관리하고, `.env.example`에는 필요한 변수명과 비밀이 아닌 예시만 기록한다.

## 5. Git 협업 규칙

### 5.1 브랜치

기본 통합 브랜치는 `develop`으로 사용하고, 기능 작업은 별도의 브랜치에서 진행한다.

| 작업 유형 | 접두사 | 예시 |
|---|---|---|
| 기능 개발 | `feature/` | `feature/b-accounts-history` |
| 버그 수정 | `fix/` | `fix/auth-validation` |
| 문서 작성 | `docs/` | `docs/project-conventions` |
| 리팩터링 | `refactor/` | `refactor/account-service` |

브랜치명은 소문자와 하이픈을 사용하고, 작업 목적을 짧게 표현한다.

### 5.2 커밋 메시지

커밋 메시지는 Conventional Commits 형식을 기본으로 사용한다.

```text
<type>: <변경 내용>
```

주요 유형:

- `feat`: 새로운 기능 추가
- `fix`: 버그 수정
- `docs`: 문서 변경
- `refactor`: 기능 변경 없는 코드 구조 개선
- `test`: 테스트 추가 또는 수정
- `chore`: 설정 및 기타 유지보수 작업

예시:

```text
feat: 사용자 계정 및 대화 기록 기능 구현
fix: 대화 기록 소유권 검사 수정
docs: 프로젝트 개발 컨벤션 추가
refactor: 계정 서비스 책임 분리
test: 인증 서비스 테스트 추가
```

한 커밋에는 가능한 한 하나의 논리적인 변경 사항을 담는다.

### 5.3 Pull Request

- 기능 브랜치의 변경 사항은 `develop`을 대상으로 PR을 생성한다.
- `main`에 직접 기능을 push하지 않는다.
- PR 제목은 변경 목적이 명확하게 드러나도록 작성한다.
- PR 본문에는 작업 내용, 검증 결과, 통합 시 확인 사항을 기록한다.
- 팀장 또는 동료의 리뷰를 요청하고, 리뷰 의견은 해당 작업 브랜치에서 수정한다.
- 수정 사항을 같은 브랜치에 push하면 기존 PR에 반영된다.
- 팀의 리뷰 및 병합 절차를 따른다.

### 5.4 PR 작성 템플릿

```markdown
## 작업 내용
- 구현하거나 수정한 기능

## 검증 결과
- [x] 실행한 테스트 및 확인 결과
- [ ] 검증하지 못한 항목

## 통합 시 확인 사항
- API 및 DB 규격 변경
- 다른 담당자의 작업에 미치는 영향
- 남아 있는 문제 및 후속 작업

---
리뷰어에게 전달할 내용, 추가 논의 사항 등 기타 전달 사항
```

## 6. 테스트 및 검증

- 기능을 변경한 경우 관련 테스트를 실행한다.
- 인증, 사용자 소유권, DB 저장·조회처럼 데이터 보호에 영향을 주는 기능은 정상 상황과 실패 상황을 함께 확인한다.
- PR에는 실제로 실행한 검증만 완료된 것으로 기록한다.
- 테스트를 실행하지 못했다면 그 이유와 남은 검증 항목을 명시한다.
- 전체 통합 테스트는 담당 기능별 검증과 구분해 기록한다.

## 7. 컨벤션 변경

- 공통 API, DB 스키마, 인증 방식 또는 응답 형식 변경은 관련 담당자와 먼저 협의한다.
- 본 문서의 규칙을 변경할 때는 변경 이유와 영향을 설명하고 팀 리뷰를 거친다.
- 기존 코드와 문서가 충돌하면 임의로 판단하지 않고 관련 담당자와 적용 기준을 정한다.
