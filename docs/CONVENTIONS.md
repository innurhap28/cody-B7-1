# 프로젝트 개발 컨벤션

## 1. 목적

이 문서는 STORY / REELS 프로젝트의 코드 작성 방식과 Git 협업 규칙을 통일하기 위한 기준을 정의한다. 코드 가독성을 유지하고 A·B·C 담당자의 작업을 원활하게 통합하는 것을 목표로 한다.

본 문서는 팀 공통 컨벤션 초안이며, API·DB 구조 및 공통 필드 변경은 관련 담당자와 합의한 뒤 적용한다.

## 2. 코드 작성 규칙

### 2.1 Python 네이밍

- 변수명과 함수명은 `snake_case`를 사용한다.
- 클래스명은 `PascalCase`를 사용한다.
- 상수명은 `UPPER_SNAKE_CASE`를 사용한다.
- 함수와 변수는 역할을 명확하게 나타내는 이름을 사용한다.
- 한 함수는 가능한 한 하나의 책임을 갖도록 작성한다.

```python
def get_user_conversations(user_id: int):
    ...

class ConversationService:
    ...

MAX_HISTORY_COUNT = 50
```

### 2.2 파일 및 모듈 구성

- 관련 기능은 목적에 맞는 디렉터리와 모듈로 분리한다.
- 파일 하나에 서로 다른 계층의 책임을 과도하게 집중하지 않는다.
- 기존 프로젝트의 디렉터리 구조를 우선 따르며, 구조 변경이 필요하면 팀원과 공유한다.

권장 역할은 다음과 같다.

| 영역 | 책임 |
|---|---|
| `routers/` | HTTP 요청 처리 및 응답 반환 |
| `schemas/` | 요청·응답 데이터 검증 |
| `models/` | 데이터베이스 모델 정의 |
| `services/` | 핵심 비즈니스 로직 |
| `dependencies.py` | 공통 의존성 주입 |
| `database.py` | DB 연결 및 세션 관리 |
| `security.py` | 인증 및 보안 관련 기능 |

실제 파일 구조와 기존 코드가 우선이며, 모든 기능을 반드시 위 구조에 맞춰 새로 분리할 필요는 없다.

## 3. API 컨벤션

### 3.1 엔드포인트

- URL은 리소스를 기준으로 작성한다.
- HTTP 메서드는 작업의 의미에 맞게 사용한다.
- 기존 엔드포인트를 변경하거나 삭제할 때는 호출하는 담당자와 먼저 조율한다.

예시:

```text
POST   /auth/register
POST   /auth/login
GET    /conversations
POST   /conversations
GET    /conversations/{conversation_id}
```

위 경로는 예시이며, 실제 프로젝트에서 이미 사용 중인 API 규격과 일치하는지 확인한 뒤 적용한다.

### 3.2 요청 및 응답

- 요청과 응답의 데이터 구조는 Pydantic 스키마로 명시한다.
- 필드명, 자료형, 필수 여부, 오류 응답 형식을 일관되게 유지한다.
- 공통 응답 형식을 도입하거나 변경할 때는 A·B·C 담당자가 함께 합의한다.
- 기존 API의 요청·응답 구조를 임의로 변경하지 않는다.

### 3.3 HTTP 상태 코드

- `200 OK`: 요청 성공
- `201 Created`: 리소스 생성 성공
- `204 No Content`: 응답 본문 없이 요청 성공
- `400 Bad Request`: 잘못된 요청
- `401 Unauthorized`: 인증 정보가 없거나 유효하지 않음
- `403 Forbidden`: 접근 권한 없음
- `404 Not Found`: 리소스를 찾을 수 없음
- `422 Unprocessable Entity`: 요청 데이터 검증 실패
- `500 Internal Server Error`: 예상하지 못한 서버 오류

상태 코드는 실제 오류 상황에 맞게 선택하고, 기존 API의 동작과 일관성을 유지한다.

## 4. DB 및 인증 컨벤션

- DB 모델과 필드의 이름, 자료형, 제약 조건을 명확하게 정의한다.
- DB 스키마 변경은 관련 API 및 서비스에 미치는 영향을 확인한 뒤 적용한다.
- 인증이 필요한 API는 프로젝트의 공통 인증 의존성을 사용한다.
- 사용자 소유 리소스는 서버에서 인증된 사용자 정보를 기준으로 접근 권한을 확인한다.
- 요청으로 전달된 사용자 ID만 신뢰해 다른 사용자의 데이터에 접근하도록 허용하지 않는다.
- 비밀번호는 평문으로 저장하지 않고 안전한 해시 방식으로 처리한다.
- 비밀 키, DB 비밀번호, 토큰 등 민감한 정보는 소스 코드에 직접 작성하거나 Git에 커밋하지 않는다.

### 4.1 환경 변수 및 민감정보 관리

- `.env` 파일에는 API 키, 인증 비밀키, DB 접속 정보 등 환경별 설정과 민감정보를 저장할 수 있다.
- `.env`, `.env.*` 등 실제 비밀정보가 포함된 파일은 `.gitignore`에 등록한다. 단, 공유해도 되는 `.env.example`은 예외로 관리한다.
- `.env.example`에는 필요한 변수명과 비밀이 아닌 예시만 기록한다. 실제 API 키, 비밀번호, 토큰은 포함하지 않는다.
- 애플리케이션은 환경 변수 또는 이에 준하는 안전한 설정 주입 방식을 통해 민감정보를 읽는다.
- 필수 환경 변수가 없거나 잘못된 경우 애플리케이션 시작 단계에서 원인을 파악할 수 있도록 처리한다. 오류 메시지에 실제 비밀값을 포함하지 않는다.
- 배포 환경에서는 서버 또는 호스팅 플랫폼이 제공하는 환경 변수·비밀정보 관리 기능을 우선 사용한다.
- 배포 플랫폼에서 환경 변수 등록 및 주입이 가능한지 실제 배포 과정에서 확인한다.
- `.gitignore` 등록은 이미 Git에 추적되거나 원격 저장소에 공개된 파일을 자동으로 제거하지 않는다. 기존에 추적 중인 민감정보 파일은 별도로 추적을 해제하고, 노출된 비밀정보는 폐기·재발급한다.

## 5. AI API, 로그 및 자료 관리

### 5.1 AI API 관리

- AI API 키는 환경 변수 또는 안전한 비밀정보 관리 기능으로 관리한다.
- API 키를 프론트엔드 코드, 공개 저장소, README, 커밋 메시지에 포함하지 않는다.
- 모델명과 요청 설정은 가능한 한 환경 설정 또는 별도 설정 모듈에서 관리한다.
- API 호출 실패, 응답 지연, 사용량 제한 및 비용을 고려해 예외 처리를 구현한다.
- 사용자 입력과 대화 기록을 외부 AI 서비스로 전송할 때는 필요한 데이터만 전달하고, 불필요한 개인정보나 민감정보를 포함하지 않는다.
- AI API의 모델이나 요청·응답 규격을 변경할 때는 해당 기능을 사용하는 담당자와 공유한다.

### 5.2 로그 관리

- 로그는 오류 원인 파악과 서비스 동작 확인에 필요한 정보 위주로 기록한다.
- API 키, 비밀번호, 인증 토큰, DB 접속 정보 등 비밀정보를 로그에 기록하지 않는다.
- 사용자 대화 내용과 개인정보는 기본적으로 로그에 기록하지 않는다. 디버깅 목적으로 필요한 경우에도 최소한의 데이터만 사용하고 민감정보를 제거한다.
- 로컬 로그 파일과 디버깅 산출물은 Git에 커밋하지 않는다.
- 로그 파일의 보관 기간, 접근 권한 및 삭제 기준은 배포 환경과 운영 요구사항에 맞춰 정한다.
- 오류 로그에는 원인 파악에 필요한 오류 유형과 요청 맥락을 남기되, 민감한 요청 본문이나 인증 정보를 노출하지 않는다.

### 5.3 이론 자료 및 데이터 관리

- 외부 문서, 논문, 데이터셋 등을 활용하는 경우 출처와 이용 조건을 확인한다.
- 외부 자료를 프로젝트에 포함하거나 수정해 활용할 때는 필요한 출처와 라이선스 정보를 기록한다.
- 용량이 큰 데이터, 재생성 가능한 산출물 및 민감한 원본 데이터는 무분별하게 Git에 포함하지 않는다.
- 데이터 파일의 저장 위치와 사용 목적을 명확하게 하고, 필요한 경우 README 또는 별도 자료 목록에 기록한다.
- 개인정보나 사용 권한이 불명확한 자료는 임의로 저장하거나 외부 AI 서비스에 전송하지 않는다.
- AI 응답 생성에 사용하는 참고 자료와 실제 학습 데이터는 구분한다. 프로젝트에서 모델 학습을 수행하지 않는다면 참고 자료를 학습 데이터라고 표현하지 않는다.

## 6. Git 협업 규칙

### 6.1 브랜치

기본 통합 브랜치는 `develop`으로 사용하고, 기능 작업은 별도의 브랜치에서 진행한다.

| 작업 유형 | 접두사 | 예시 |
|---|---|---|
| 기능 개발 | `feature/` | `feature/b-accounts-history` |
| 버그 수정 | `fix/` | `fix/auth-validation` |
| 문서 작성 | `docs/` | `docs/project-conventions` |
| 리팩터링 | `refactor/` | `refactor/account-service` |

- 브랜치명은 소문자와 하이픈을 사용하고 작업 목적을 짧게 표현한다.
- 작업을 시작하기 전에 대상 브랜치의 최신 변경 사항을 가져온다.
- 기능 브랜치에서 작업하고, 작업 결과는 PR을 통해 `develop`에 통합한다.
- `main`에 직접 기능을 push하지 않는다.

### 6.2 커밋 메시지

커밋 메시지는 Conventional Commits 형식을 기본으로 사용한다.

```text
<type>: <변경 내용>
```

주요 유형:

- `feat`: 새로운 기능 추가
- `fix`: 버그 수정
- `docs`: 문서 변경
- `refactor`: 기능 변경 없는 코드 구조 개선
- `test`: 테스트 추가 또는 수정
- `chore`: 설정 및 기타 유지보수 작업

예시:

```text
feat: 사용자 계정 및 대화 기록 기능 구현
fix: 대화 기록 소유권 검사 수정
docs: 프로젝트 개발 컨벤션 추가
refactor: 계정 서비스 책임 분리
test: 인증 서비스 테스트 추가
```

- 한 커밋에는 가능한 한 하나의 논리적인 변경 사항을 담는다.
- 커밋 메시지는 변경 목적을 이해할 수 있도록 작성한다.
- 개인별 작업 이력을 확인할 수 있도록 각자 본인이 수행한 작업을 자신의 계정으로 커밋한다.
- 다른 사람의 작업을 대신 커밋하거나 커밋 작성자를 오인하게 하는 방식으로 기록하지 않는다.

### 6.3 Pull Request

- 기능 브랜치의 변경 사항은 `develop`을 대상으로 PR을 생성한다.
- PR 제목은 변경 목적이 명확하게 드러나도록 작성한다.
- PR 본문에는 작업 내용, 검증 결과, 통합 시 확인 사항을 기록한다.
- 팀장 또는 동료의 리뷰를 요청하고, 리뷰 의견은 해당 작업 브랜치에서 수정한다.
- 수정 사항을 같은 브랜치에 push하면 기존 PR에 반영된다.
- API, DB 스키마, 인증 방식 또는 공통 응답 규격이 변경되면 관련 담당자와 영향을 확인한다.
- 검증하지 못한 항목은 완료된 것으로 표시하지 않고, 미검증 사유와 후속 계획을 작성한다.

### 6.4 리뷰 및 병합 방식

- `develop`으로의 병합은 PR을 통해 진행한다.
- 팀 공통 병합 방식은 **Create a merge commit (일반 Merge)** 을 기본안으로 한다.
- 일반 Merge를 사용해 기능 브랜치의 개별 커밋 이력과 병합 이력을 보존한다.
- 리뷰 승인 및 필요한 검증이 완료된 뒤 병합한다. 실제 승인 개수와 병합 제한은 저장소 규칙 설정을 따른다.
- 개인별 기여도는 커밋 이력만으로 판단하지 않고, PR 내용, 변경 코드, 담당 기능 및 리뷰 기록을 함께 확인한다.
- Squash and merge 등 다른 병합 방식이 필요한 경우 팀원과 합의한 뒤 적용한다.
- GitHub 저장소에서 일반 Merge를 사용할 수 있도록 `Allow merge commits` 설정을 확인한다.

위 병합 정책은 팀 검토용 초안이다. 과제에서 요구하는 개인별 커밋 이력 확인 방식과 저장소 설정을 확인한 뒤 최종 확정한다.

### 6.5 PR 작성 템플릿

```markdown
## 작업 내용
- 구현하거나 수정한 기능
- 주요 변경 사항 및 변경 목적

## 검증 결과
- [x] 실행한 테스트 및 확인 결과
- [ ] 검증하지 못한 항목 및 미검증 사유

## 통합 시 확인 사항
- API 및 DB 규격 변경 사항
- 다른 담당자의 작업에 미치는 영향
- 남아 있는 문제 및 후속 작업

---

## 기타 전달 사항 (선택)
- 리뷰어에게 전달할 내용
- 추가 논의가 필요한 사항
```

## 7. 테스트 및 검증

- 기능을 변경한 경우 관련 테스트를 실행한다.
- 인증, 사용자 소유권, DB 저장·조회처럼 데이터 보호에 영향을 주는 기능은 정상 상황과 실패 상황을 함께 확인한다.
- PR에는 실제로 실행한 검증만 완료된 것으로 기록한다.
- 테스트를 실행하지 못했다면 그 이유와 남은 검증 항목을 명시한다.
- 전체 통합 테스트는 담당 기능별 검증과 구분해 기록한다.
- 환경 변수나 배포 설정을 변경한 경우 필요한 설정이 실제 실행 환경에서 정상적으로 적용되는지 확인한다.
- AI API를 사용하는 기능은 성공 응답뿐 아니라 API 오류, 응답 지연 및 사용량 제한 상황도 고려한다.

## 8. 컨벤션 변경

- 공통 API, DB 스키마, 인증 방식 또는 응답 형식 변경은 관련 담당자와 먼저 협의한다.
- 본 문서의 규칙을 변경할 때는 변경 이유와 영향을 설명하고 팀 리뷰를 거친다.
